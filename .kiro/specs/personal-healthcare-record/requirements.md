# 要件定義書

## はじめに

本ドキュメントでは、個人ヘルスケアレコード（PHR: Personal Healthcare Record）管理システムの要件を定義します。このシステムは、日々の健康情報を記録・蓄積・分析し、医療機関との情報共有を支援するWebアプリケーションです。

### ビジネス価値

- **継続的な健康管理**: ユーザーが日々の健康情報を継続的に記録し、長期的な健康状態を把握できる
- **データ分析による気づき**: 蓄積されたデータから傾向を可視化し、健康改善のための気づきを提供
- **医療機関との円滑な連携**: 定期健診時にかかりつけ医へ健康データを効率的に報告できる
- **シンプルさと柔軟性**: 既存サービスの「過剰機能」と「機能不足」の間のギャップを埋める、使いやすいツール

### ビジネス目標

本システムは、以下のビジネス目標を段階的に達成します：

1. **ユーザーの継続利用促進**: 月次アクティブユーザー率80%以上（サービス開始後6ヶ月）
2. **データ登録の利便性向上**: 平均データ登録時間30秒以内（サービス開始時点）
3. **データ分析機能の充実**: 分析機能利用率 月1回以上の利用70%以上（サービス開始後3ヶ月）
4. **医師との情報共有の実現**: データ出力機能利用率 年1回以上の利用50%以上（サービス開始後1年）

### ステークホルダー

- **SH-01: システム利用者（個人ユーザー）**: 日々の健康情報を記録・管理する主体
- **SH-02: かかりつけ医/医療従事者**: 患者の健康データを受け取り、診療や健康指導に活用
- **SH-03: システム管理者**: データ種類マスタの設定・管理を担当
- **SH-04: システム運用者**: システムの稼働監視、バックアップ、障害対応を担当

## 要件

### 要件1: ユーザー認証とアクセス制御

**目的:** システム利用者として、自身の健康情報を安全に保護し、許可されたユーザーのみがアクセスできるようにしたい。これにより、個人の機密性の高い健康情報を不正アクセスから守る。

#### 受入基準

1. WHEN ユーザーがシステムにアクセスする THEN SPHRはBasic認証を要求する
2. WHEN ユーザーが正しいユーザー名とパスワードを入力する THEN SPHRは認証を許可し、ホーム画面を表示する
3. WHEN ユーザーが誤ったユーザー名またはパスワードを入力する THEN SPHRは認証を拒否し、エラーメッセージを表示する
4. WHEN ユーザーがログインに成功する THEN SPHRはHTTPSセッションを確立し、セキュアなクッキーを発行する
5. WHERE SPHRがユーザー認証を行う THE SPHRはTLS 1.2以上の暗号化通信を使用する
6. WHEN ユーザーが自身の健康データにアクセスする THEN SPHRは当該ユーザーのデータのみを表示し、他のユーザーのデータへのアクセスを拒否する
7. WHEN ユーザーが新規アカウントを作成する THEN SPHRはパスワードを最小8文字、英数字混在で要求し、bcryptによりハッシュ化して保存する
8. WHEN データ登録、変更、削除、参照の操作が実行される THEN SPHRはアクセスログと操作ログ（ユーザーID、操作種別、対象データID、操作日時）を記録する

---

### 要件2: 健康情報登録

**目的:** システム利用者として、日々の健康情報（血圧、脈拍、体重等）をスマホやPCから簡単に登録できるようにしたい。これにより、毎日の健康状態を継続的に記録し、長期的なデータ蓄積が可能になる。

#### 受入基準

1. WHEN ユーザーが健康情報登録画面を開く THEN SPHRは登録可能なデータ種類の一覧（血圧上、血圧下、脈拍、体重等）を表示順に表示する
2. WHEN ユーザーがデータ種類を選択する THEN SPHRは選択されたデータ種類に対応する入力フォーム（測定値、測定日、メモ）を表示する
3. WHEN ユーザーが測定値（数値）、測定日（日付）を入力し登録ボタンをクリックする THEN SPHRは入力値を検証し、妥当であればデータベースに保存する
4. WHEN データ登録処理が完了する THEN SPHRは1秒以内にレスポンスを返し、成功メッセージを表示する
5. WHEN ユーザーが入力値に不正な値（数値形式エラー、未来日付、必須項目未入力等）を含む THEN SPHRはわかりやすいエラーメッセージ（「測定値は数値で入力してください」等）を表示し、データは保存しない
6. WHEN ユーザーが登録済みのデータを選択して変更ボタンをクリックする THEN SPHRは編集可能な入力フォームを表示する
7. WHEN ユーザーが変更内容を保存する THEN SPHRは変更内容をデータベースに反映し、操作完了を通知する
8. WHEN ユーザーが登録済みのデータを選択して削除ボタンをクリックする THEN SPHRは確認ダイアログを表示し、ユーザーの承認後にデータを削除する
9. WHEN データ登録、変更、削除の操作が実行される THEN SPHRは操作ログ（ユーザーID、操作種別、対象データID、操作日時）を記録する
10. WHERE ユーザーがスマートフォンまたはPCからアクセスする THE SPHRは各デバイスに最適化された表示形式（レスポンシブデザイン）を提供する

---

### 要件3: 健康情報参照

**目的:** システム利用者として、過去に登録した健康情報を日付や期間を指定して参照したい。これにより、自身の健康状態の推移を確認できる。

#### 受入基準

1. WHEN ユーザーが健康情報参照画面を開く THEN SPHRは直近30日間のデータを時系列順（新しい順）に一覧表示する
2. WHEN ユーザーが期間（開始日、終了日）とデータ種類を指定して検索する THEN SPHRは条件に合致するデータを時系列順に表示する
3. WHEN データ参照のレスポンス時間を測定する THEN SPHRは2秒以内に結果を表示する
4. WHEN データ件数が100件を超える THEN SPHRはページネーションまたは無限スクロールによる表示制御を行う
5. WHEN ユーザーが一覧表示されたデータの1件を選択する THEN SPHRは詳細情報（データ種類、測定値、単位、測定日、メモ）を表示する
6. WHERE ユーザーがスマートフォンまたはPCからアクセスする THE SPHRは各デバイスに最適化された表示形式（レスポンシブデザイン）を提供する

---

### 要件4: データ種類管理

**目的:** システム管理者として、血圧（上）、血圧（下）、脈拍、体重などのデータ種類をマスタデータとして管理したい。これにより、ユーザーが記録できる健康情報の項目を柔軟に設定できる。

#### 受入基準

1. WHEN システム管理者がデータ種類管理画面を開く THEN SPHRは既存のデータ種類一覧（データ種類名、単位、表示順、有効/無効状態）を表示する
2. WHEN システム管理者が新しいデータ種類を追加する THEN SPHRはデータ種類名、単位、表示順を入力するフォームを表示する
3. WHEN システム管理者がデータ種類情報を入力し登録ボタンをクリックする THEN SPHRは入力値を検証し、データ種類マスタに追加する
4. WHEN システム管理者が既存のデータ種類を編集する THEN SPHRはデータ種類名、単位、表示順を変更可能なフォームを表示する
5. WHEN システム管理者がデータ種類を無効化する THEN SPHRは論理削除（is_active=false）を実行し、ユーザーの登録画面から非表示にする
6. WHEN 無効化されたデータ種類に関連する既存の健康データが存在する THEN SPHRは既存データを保持し、参照は可能だが新規登録は不可とする
7. WHEN システム初期化時 THEN SPHRはデフォルトのデータ種類（血圧上、血圧下、脈拍、体重）を自動登録する

---

### 要件5: データ分析

**目的:** システム利用者として、蓄積された健康データから傾向を把握し、統計値やグラフで視覚的に健康状態を理解したい。これにより、健康改善のための気づきを得られる。

#### 受入基準

1. WHEN ユーザーがデータ分析画面を開く THEN SPHRは分析対象のデータ種類選択と期間指定のフォームを表示する
2. WHEN ユーザーがデータ種類（血圧上等）と期間（開始日、終了日）を指定して分析ボタンをクリックする THEN SPHRは以下の統計値を計算し表示する：最大値、最小値、平均値
3. WHEN 統計値の計算が完了する THEN SPHRは3秒以内に結果を表示する
4. WHEN ユーザーがグラフ表示を選択する THEN SPHRは折れ線グラフを描画し、X軸に測定日、Y軸に測定値をプロットする
5. WHEN ユーザーが30日移動平均を選択する THEN SPHRは移動平均値を計算し、折れ線グラフに重ねて表示する
6. WHEN グラフ描画が完了する THEN SPHRは3秒以内にグラフを表示する
7. WHERE ユーザーがスマートフォンからアクセスする THE SPHRはタッチ操作に対応したインタラクティブなグラフを提供する
8. WHEN ユーザーが複数のデータ種類を同時に比較表示する THEN SPHRは複数の折れ線グラフを異なる色で同一グラフ上に表示する
9. IF 選択期間にデータが存在しない THEN SPHRは「データがありません」というメッセージを表示する

---

### 要件6: データ出力

**目的:** システム利用者として、指定期間の健康データをPDF、CSV等の形式で出力し、医療機関へ提供したい。これにより、定期健診時にかかりつけ医へ効率的に健康データを報告できる。

#### 受入基準

1. WHEN ユーザーがデータ出力画面を開く THEN SPHRは出力期間（開始日、終了日）と出力形式（PDF、CSV）の選択フォームを表示する
2. WHEN ユーザーが期間と出力形式を指定して出力ボタンをクリックする THEN SPHRは指定期間のすべての健康データを出力形式に応じて生成する
3. WHEN PDF形式が選択される THEN SPHRは統計値（最大、最小、平均）、データ一覧表、折れ線グラフを含むレポートを生成する
4. WHEN CSV形式が選択される THEN SPHRは測定日、データ種類名、測定値、単位、メモをカンマ区切り形式で生成する
5. WHEN データ出力処理が完了する THEN SPHRは10秒以内（1年分のデータを想定）に出力ファイルをダウンロード可能にする
6. WHEN データ出力が完了する THEN SPHRは出力履歴（ユーザーID、開始日、終了日、出力形式、出力日時）を記録する
7. WHEN PDF出力を実行する THEN SPHRは医療機関へ提出しやすい形式（日付、データ種類、測定値を表形式で整理）でレイアウトする

---

### 要件7: 過去データ移行

**目的:** システム利用者として、既存の3年分のデータをCSV形式から新システムへ移行したい。これにより、初日から長期的なデータ分析が可能になる。

#### 受入基準

1. WHEN ユーザーがデータインポート画面を開く THEN SPHRはCSVファイルアップロードフォームとCSVフォーマット説明を表示する
2. WHEN ユーザーがCSVファイル（測定日、データ種類名、測定値、メモを含む）をアップロードする THEN SPHRはファイル形式を検証する
3. WHEN CSVファイルの形式が正しい THEN SPHRは各行を解析し、データ種類名をマスタデータと照合する
4. WHEN CSVファイルのデータ種類名がマスタに存在する THEN SPHRは健康データとしてデータベースに登録する
5. WHEN CSVファイルのデータ種類名がマスタに存在しない THEN SPHRはエラー行として記録し、インポート完了後にエラーレポートを表示する
6. WHEN インポート処理が完了する THEN SPHRは成功件数、失敗件数、エラー詳細を表示する
7. WHEN データインポートが実行される THEN SPHRは操作ログ（ユーザーID、ファイル名、成功件数、失敗件数、インポート日時）を記録する
8. IF CSVファイルの形式が不正である（必須カラムが不足等） THEN SPHRはエラーメッセージを表示し、インポートを中止する

---

## 非機能要件

### 非機能要件1: 性能

**目的:** システムが快適に利用できるレスポンス時間を維持し、ユーザーの継続利用を促進する。

#### 受入基準

1. WHEN ユーザーがデータ登録操作を実行する THEN SPHRは1秒以内にレスポンスを返す
2. WHEN ユーザーがデータ参照操作を実行する THEN SPHRは2秒以内に結果を表示する
3. WHEN ユーザーがグラフ描画操作を実行する THEN SPHRは3秒以内にグラフを表示する
4. WHEN ユーザーがデータ出力操作を実行する（1年分データ） THEN SPHRは10秒以内に出力ファイルを生成する
5. WHEN システムの同時接続ユーザー数が20名以下である THEN SPHRは上記の性能目標を維持する
6. WHERE 性能目標を達成する THE SPHRは適切なデータベースインデックス（user_id、measurement_date、data_type_id）を設定する

---

### 非機能要件2: セキュリティ

**目的:** 個人の健康情報という機密性の高いデータを不正アクセス、データ漏洩、各種攻撃から保護する。

#### 受入基準

1. WHERE SPHRがHTTP通信を行う THE SPHRはTLS 1.2以上の暗号化を使用する
2. WHEN ユーザーがパスワードを設定する THEN SPHRはbcryptによりソルト付きでハッシュ化し、平文パスワードを保存しない
3. WHEN SPHRがデータベースクエリを実行する THEN SPHRはプリペアドステートメントを使用し、SQLインジェクション攻撃を防止する
4. WHEN SPHRがユーザー入力を表示する THEN SPHRは入力値をサニタイジング・エスケープ処理し、XSS攻撃を防止する
5. WHEN SPHRが状態変更操作（登録、変更、削除）を実行する THEN SPHRはCSRFトークンを検証し、CSRF攻撃を防止する
6. WHEN ユーザーが他のユーザーのデータにアクセスを試みる THEN SPHRはアクセスを拒否し、エラーメッセージを表示する
7. WHEN システム管理者がOSまたはミドルウェアのセキュリティパッチをリリースする THEN SPHRは月次（OS）または随時（ミドルウェア）でパッチを適用する
8. WHEN ファイアウォール設定を構成する THEN SPHRはHTTPS（443）とSSH（22）のみを開放する
9. WHEN 不正アクセス試行を検知する THEN SPHRはアクセスログから異常なアクセスパターンを監視し、セキュリティインシデントを記録する

---

### 非機能要件3: 可用性

**目的:** システムが安定稼働し、ユーザーがいつでもデータ登録・参照できるようにする。

#### 受入基準

1. WHEN システムの年間稼働時間を測定する THEN SPHRは99.5%以上の稼働率を達成する（月間約3.6時間の停止を許容）
2. WHEN 計画メンテナンスを実施する THEN SPHRは月1回、深夜時間帯（2:00〜4:00）、最大2時間以内に完了する
3. WHEN 計画メンテナンスを実施する THEN SPHRは1週間前にユーザーへ通知する
4. WHEN 障害が発生する THEN SPHRは5分以内に自動監視ツールにより障害を検知する
5. WHEN 障害が検知される THEN SPHRは4時間以内に復旧する（RTO: 目標復旧時間）
6. WHEN データベースのバックアップを実行する THEN SPHRは日次（午前3:00）で自動的にフルバックアップを実行する
7. WHEN バックアップからデータを復旧する THEN SPHRは24時間以内のデータ損失を許容する（RPO: 目標復旧時点）
8. WHEN バックアップデータを保存する THEN SPHRはAzureストレージ（別リージョン）に30日間保存する
9. WHEN 月次で復旧テストを実施する THEN システム管理者はバックアップからの復旧手順を検証し、結果を記録する

---

### 非機能要件4: ユーザビリティ

**目的:** シンプルで直感的なUI/UXにより、ユーザーがストレスなくデータ登録・分析を継続できるようにする。

#### 受入基準

1. WHEN ユーザーが1件の健康情報を登録する THEN SPHRは30秒以内に登録完了できるUI/UXを提供する
2. WHEN 新規ユーザーがシステムを初めて利用する THEN SPHRは10分以内に基本操作（登録、参照、分析）を習得できるUI/UXを提供する
3. WHERE ユーザーがスマートフォンまたはPCからアクセスする THE SPHRはレスポンシブデザインにより各デバイスで最適表示を提供する
4. WHEN ユーザーが入力エラーを発生させる THEN SPHRはわかりやすいエラーメッセージ（「測定値は数値で入力してください」等）を表示する
5. WHERE SPHRが高齢者ユーザーを対象とする THE SPHRは文字サイズの調整、高コントラストモード対応を提供する
6. WHEN システム満足度を測定する THEN SPHRは5段階評価で4.0以上を達成する
7. WHEN スマートフォンでデータ登録を行う THEN SPHRは操作成功率99%以上を維持する
8. WHEN PCでデータ登録を行う THEN SPHRは操作成功率99%以上を維持する

---

### 非機能要件5: 運用・保守性

**目的:** 低コストな運用体制を維持しながら、安定したシステム運用とユーザーサポートを提供する。

#### 受入基準

1. WHEN システムの運用コストを測定する THEN SPHRはユーザー1人あたり月額100円以下を達成する
2. WHEN システムの運用体制を構築する THEN SPHRは1〜2名体制（開発兼任）で運用する
3. WHEN システムの監視を実施する THEN SPHRは自動監視ツール（Prometheus等）により基本監視（死活監視、CPU、メモリ、ディスク、レスポンス時間）を1分間隔で実行する
4. WHEN 監視アラートが発生する THEN SPHRはメール通知（システム管理者宛）を送信する
5. WHEN ユーザーがサポートを要求する THEN SPHRはメール問い合わせのみを受け付け、営業日24時間以内に回答する
6. WHEN システムのログを保存する THEN SPHRはアクセスログを1年間、エラーログを3年間保存する
7. WHEN システムのデプロイを実行する THEN SPHRはDocker Composeによる自動デプロイを使用する
8. WHEN システム更新を実施する THEN SPHRは機能追加を四半期ごと、セキュリティパッチを随時適用する
9. WHEN よくある質問（FAQ）をWebページで公開する THEN SPHRは問い合わせ負荷を軽減する

---

### 非機能要件6: 拡張性

**目的:** ユーザー数とデータ量の増加に応じて、システムを段階的に拡張できるようにする。

#### 受入基準

1. WHEN 初期フェーズ（100ユーザー）を開始する THEN SPHRはvCPU 2コア、メモリ4GB、ストレージ100GBのVM構成で稼働する
2. WHEN ユーザー数が500名に達する THEN SPHRはVMスペックの見直しを実施し、必要に応じてスケールアップする
3. WHEN ユーザー数が1,000名に達する THEN SPHRはvCPU 4コア、メモリ8GB、ストレージ500GBのVM構成へスケールアップする
4. WHEN VMスケールアップを実施する THEN SPHRは計画メンテナンス時間内（最大2時間）に完了する
5. WHEN データ量の増加を想定する THEN SPHRは初年度20万件/年から3年後200万件/年のデータ登録に対応できる設計とする

## まとめ

本要件定義書は、個人ヘルスケアレコード管理システムの7つの機能要件と6つの非機能要件を定義しました。

**機能要件**:
1. ユーザー認証とアクセス制御 - セキュリティの基盤
2. 健康情報登録 - システムの中核機能
3. 健康情報参照 - データ確認と履歴把握
4. データ種類管理 - 柔軟なカスタマイズ性
5. データ分析 - 統計値とグラフによる気づき
6. データ出力 - 医療機関との情報共有
7. 過去データ移行 - 既存データの活用

**非機能要件**:
1. 性能 - レスポンス時間1〜10秒以内
2. セキュリティ - TLS、暗号化、各種攻撃対策
3. 可用性 - 稼働率99.5%、RTO 4時間、RPO 24時間
4. ユーザビリティ - 登録30秒以内、満足度4.0以上
5. 運用・保守性 - 低コスト運用、1〜2名体制
6. 拡張性 - 100〜1,000ユーザーへの段階的拡張

これらの要件は、EARS形式の受入基準により明確化され、テスト可能な形で定義されています。次のフェーズでは、これらの要件を実現するための技術設計を作成します。
